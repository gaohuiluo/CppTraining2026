# M4 内存管理与 RAII

> 你在 C 里管理堆内存的方式是：`malloc` 拿内存，用完 `free`，中间靠自己记着。写了这么多年 C，你大概率被泄漏、悬垂指针、double free 都咬过。这一模块要回答的不是「C++ 有哪些新工具」，而是一个更根本的问题：**手动配对为什么必然出错？语言能提供什么机制把它根治？** 顺着这条线走到底，你会发现智能指针不是「又一套 API」，而是从一条语言级保证一步步推导出来的必然结果。

---

## 0. 一句话总览与全文主线

**内存管理的终极目标：每一块资源都有明确的「拥有者」，拥有者消失的那一刻，资源自动释放。C++ 的做法是抓住「析构一定会被调用」这条语言级保证，把释放动作挂上去，让它从「程序员的纪律」变成「编译器的工作」。**

全文只有一条主线，每一节解决上一节遗留的问题：

```
 第 1 节                第 2 节               第 3 节
 内存的底层布局:        C++ 的堆接口:          手动配对为什么"必然"
 栈为什么快,       →    new = 分配+构造,   →   出错(不是"容易"):
 堆为什么要记账         delete = 析构+释放      退出路径爆炸,人肉配对
                                              不可扩展
                                                   │
                                                   ▼
 第 6~10 节             第 5 节               第 4 节
 把 RAII 泛化成         把资源绑到这条         语言给的保证:
 可复用的类型:     ←    保证上:          ←    无论怎么离开作用域,
 unique/shared/weak     RAII                  栈对象的析构一定被调用
        │
        ▼
 第 11~12 节
 用类型表达所有权设计:
 拥有 vs 借用,让函数签名说话
```

M2 里你已经建立了直觉：**析构 = 自动清理**。M4 做两件事：把这个直觉**挖到底**（析构为什么保证被调用、new 到底干了什么），再把它**推到极致**（用栈对象的析构去管理一切堆资源）。

## 1. 地基：进程的内存到底长什么样

先对齐底层图景。你写 C 时天天和栈、堆打交道，但「栈为什么快」「堆为什么慢」的机制值得掰开讲一次——因为后面所有推导都建立在这两点上：**栈的生命周期由语言结构决定，堆的生命周期由你决定**。

一个典型进程的地址空间（简化）：

```
高地址
┌──────────────────┐
│       栈          │ ← 向低地址增长；局部变量、函数调用的栈帧
│        ↓          │    (MSVC 默认每线程 1 MB)
│                  │
│     (空闲区)      │
│                  │
│        ↑          │
│       堆          │ ← 向高地址增长；new / malloc 的内存
├──────────────────┤
│  全局/静态数据     │ ← 全局变量、static 变量 (.data / .bss)
├──────────────────┤
│    只读数据       │ ← 字符串字面量、常量表 (.rdata)
├──────────────────┤
│    代码段         │ ← 编译出来的机器指令 (.text)
└──────────────────┘
低地址
```

代码段、只读数据、全局静态区的生命周期都是「整个程序」，不用你操心。要管理的是栈和堆——而这两者的管理方式有本质差别。

### 1.1 栈：一条指令的分配器

函数被调用时，编译器在栈顶压入一个**栈帧**（stack frame）：返回地址、保存的寄存器、以及**这个函数所有局部变量的空间**。关键在于：局部变量总共占多少字节，编译期就算好了。所以「分配」就是把栈指针挪一下：

```
call demo 之后：
    sub rsp, 64        ; 一条指令，"分配"了本函数全部 64 字节局部变量
    ...函数体...
    add rsp, 64        ; 一条指令，全部"释放"
    ret
```

这就是栈快的全部秘密：
- **分配/释放各一条指令**，没有查找、没有记账元数据；
- 内存布局连续、按调用顺序紧挨着，**天然缓存友好**；
- 代价是限制：大小要编译期基本可知、生命周期必须严格嵌套（后进先出）、总容量有限（MB 级，大数组放栈上会爆栈）。

还有一个此刻看起来平平无奇、之后会成为全文支点的事实：**编译器精确知道每个局部变量在哪个作用域结束**。栈帧和作用域是一一对应的——变量在哪行「死掉」，是编译期就确定的结构信息。先记住这句话，第 4 节回收。

### 1.2 堆：一个运行期的记账系统

堆没有「编译期已知」这种好事：要多大、什么时候要、什么时候还，全是运行期决定的。所以堆分配器（`malloc` 或 `operator new` 的底层）必须维护一套记账系统，典型实现里一次 `malloc` 要做：

1. 在**空闲块列表**（或按大小分桶的多个列表）里找一块够大的；
2. 找到后可能要**切割**（块太大就切一块给你，剩下的放回去）；
3. 在返回给你的内存**前面写块头**（记录这块多大，`free` 时要用）；
4. 空闲列表不够时，向操作系统**要新的页**（Windows 上是 `VirtualAlloc`）；
5. 多线程环境下，以上全过程要**加锁或用无锁结构同步**。

`free` 也不省事：读块头拿到大小，把块放回空闲列表，还要检查**相邻块是否空闲、能否合并**（不合并的话内存会碎成没法用的小块）。

对比一下：

| | 栈 | 堆 |
|---|---|---|
| C++ 术语 | 自动存储期（automatic） | 动态存储期（dynamic） |
| 分配动作 | 移动栈指针（1 条指令） | 查空闲列表、切块、写块头、可能加锁 |
| 释放动作 | 移动栈指针（1 条指令） | 读块头、回收、合并相邻空闲块 |
| 生命周期由谁决定 | **语言结构（作用域）** | **你（何时调 free/delete）** |
| 编译器能否自动管理 | 能——结构信息编译期已知 | 不能——它不知道你何时用完 |
| 容量 | 有限（MB 级） | 大（GB 级） |
| C 对应 | 局部变量 | `malloc` 的内存 |

### 1.3 本节结论，也是全文的问题

栈的生命周期绑定在作用域上，所以编译器**能**自动管理；堆的生命周期只有你知道，所以分配器只能等你**手动通知**（`free`/`delete`）。

什么时候必须用堆？老规矩：
- 大小/数量运行期才知道（用户输入决定的数组长度）；
- 生命周期要**超出**创建它的作用域（工厂函数返回对象）;
- 对象太大，栈放不下。

这些需求消不掉，堆必须用。于是全文要解决的问题就是：**能不能把「你手动通知」这个环节，转化成「编译器自动通知」？** 答案在第 5 节。在那之前，先看清 C++ 的堆接口比 `malloc` 多干了什么——这决定了后面所有推导的细节。

## 2. new / delete：malloc/free + 构造/析构

上一节说堆分配器「只管内存」。但 M2 讲过，C++ 对象不只是一块内存：**对象 = 内存 + 构造函数建立起来的有效状态**。所以 C++ 的堆接口必须比 `malloc` 多做一步——这一步就是 `new` 和 `malloc` 的全部区别。

### 2.1 `new` 表达式的两步分解

你写的这一行：

```cpp
Widget* p = new Widget(42);
```

编译器实际生成的是两步：

1. 调 `operator new(sizeof(Widget))` ——一个分配函数，只拿原始内存，职责和 `malloc` 完全一样（很多实现底层就是转调 `malloc`）；
2. 在这块内存上**调用构造函数** `Widget(42)`，把原始字节变成一个有效对象。

`delete p` 严格反过来：先调析构函数 `~Widget()`（清理对象持有的资源），再调 `operator delete` 还内存（职责同 `free`）。

这两步可以手动拆开演示——第 2 步用的语法叫 **placement new**（「在指定位置构造」），平时用不到，但看一次你就彻底明白 `new` 的构成了：

```cpp
#include <cstdio>
#include <new>      // placement new 需要

struct Widget {
    int id;
    explicit Widget(int i) : id(i) { std::printf("构造 %d\n", id); }
    ~Widget() { std::printf("析构 %d\n", id); }
};

int main() {
    // 你平时写的一行：
    Widget* p = new Widget(1);
    delete p;

    // 编译器实际做的两步，手动展开：
    void* mem = operator new(sizeof(Widget));   // 第 1 步：只拿内存（≈ malloc）
    Widget* q = new (mem) Widget(2);            // 第 2 步：placement new，在 mem 上调构造
    // delete 的两步，手动展开：
    q->~Widget();                               // 第 1 步：显式调析构
    operator delete(mem);                       // 第 2 步：还内存（≈ free）
}
```

### 2.2 vs C：逐条对比

| | `malloc` / `free` | `new` / `delete` |
|---|---|---|
| 构造/析构 | **不调用**，只管内存 | `new` 调构造，`delete` 调析构 |
| 类型 | 返回 `void*`，要强转 | 返回正确类型的指针，无需强转 |
| 大小 | 自己写 `sizeof(T)` | 编译器自动算 |
| 分配失败 | 返回 `NULL`，要检查 | 默认**抛 `std::bad_alloc`**，不返回空 |
| 本质 | 一个库函数 | 语言内置表达式 = 分配函数 + 构造调用 |

最本质的就是第一行。对「内部还持有资源」的类（比如成员里有 `std::string`、或自己 `new` 了东西），`malloc` 是灾难：构造函数没跑，成员是随机字节，对象根本不存在，只有一块假装是对象的内存。

由此也能**推导**出那条铁律，而不是背它：

> **`new` 配 `delete`，`malloc` 配 `free`，绝不混用。**
> 原因一：`malloc` 的内存没构造过对象，`delete` 会对随机字节调析构；`new` 的对象用 `free` 释放则跳过析构，对象持有的资源全泄漏。
> 原因二：`operator new` 和 `malloc` **不保证是同一套记账系统**（实现可以自由选择），拿 A 系统分配的块去 B 系统释放，块头对不上，堆结构直接损坏。两条原因各自都足以构成未定义行为（UB）。

### 2.3 `new[]` 的记账 cookie——推导出「不匹配为什么是 UB」

数组版本：`new Widget[3]` 要构造 3 个对象，`delete[]` 要析构 3 个。问题来了：**`delete[]` 怎么知道是 3 个？** 你没告诉它，指针里也没有这个信息。

答案：`new[]` 自己记。典型实现会在分配的内存**前面**多要几个字节，存元素个数——俗称 **cookie**：

```
new Widget[3] 的实际内存布局（典型实现）：

  ┌────────┬──────────┬──────────┬──────────┐
  │ cookie │ Widget#0 │ Widget#1 │ Widget#2 │
  │ (n=3)  │          │          │          │
  └────────┴──────────┴──────────┴──────────┘
  ↑                    ↑
  operator new[]       返回给你的指针 p 指向这里
  实际分配的起点        （cookie 之后）
```

有了这张图，`delete[] p` 的动作就清晰了：往 `p` 前面读 cookie 得到 n=3 → 逐个调 3 次析构 → 把指针**回退到真正的分配起点**交还给分配器。

现在你可以自己推出为什么 `delete p`（不带 `[]`）是 UB，而不用背了：

```cpp
Widget* ws = new Widget[3];
delete ws;    // 反例，勿模仿！
// 错误一：只调了 ws[0] 的析构，另外 2 个对象的清理逻辑没跑；
// 错误二（更致命）：delete 认为 ws 就是分配起点，直接把 ws 交给分配器，
//   但真正的起点在 cookie 处——分配器按错误地址找块头，堆记账当场损坏。
```

反过来 `delete[]` 一个普通 `new` 出来的指针也一样：它会去「指针前面」读一个根本不存在的 cookie，拿到一个随机数当元素个数。两个方向都是 UB。

一个更阴险的细节：对 `int` 这种**没有析构函数**的类型，实现不需要知道个数（不用逐个析构），通常就不加 cookie，于是 `int* a = new int[100]; delete a;` 往往「碰巧不炸」。**碰巧不炸比立刻崩溃更危险**——它让错误代码活到换编译器/换类型的那天。

> 现代 C++ 的态度：**根本别手写 `new[]`/`delete[]`**。动态数组用 `std::vector`（M7 讲）或 `std::make_unique<T[]>(n)`，cookie 这种坑让库作者去踩。

## 3. 手动配对为什么「必然」出错

工具对齐了：`new`/`delete` 是带构造析构的 `malloc`/`free`。但 C 的老问题原封不动继承了下来——**释放的时机仍然全靠你记**。这一节先把事故清单过一遍（都是你在 C 里见过的老朋友），然后证明一件更重要的事：这些事故不是「粗心」造成的，是**手动配对这个方案本身在结构上不可扩展**。

### 3.1 四类经典事故

**（1）内存泄漏**：分配了不释放。

```cpp
void leak() {
    int* p = new int[1000];
    // ... 用完忘了 delete[] p ...
}   // 栈上的指针 p 没了，堆上那 4000 字节还在——再也没人能释放它
```

隐蔽版本才是常态——不是「忘了写」，是**控制流绕过了那行 delete**：

```cpp
void tricky() {
    int* p = new int(1);
    if (some_condition()) return;   // 提前返回，绕过下面的 delete，泄漏
    mayThrow();                     // 抛异常，同样绕过，泄漏
    delete p;
}
```

**（2）悬垂指针**：内存已还给分配器，指针还在被用。

```cpp
int* p = new int(42);
delete p;            // 这块内存已经回到空闲列表，随时会被分配给别人
std::cout << *p;     // 反例，勿模仿！读已释放内存，UB
p = nullptr;         // 手动管理时的自保习惯：delete 后置空
```

**（3）double free**：同一块内存释放两次。第 1 节讲过 `free`/`delete` 要把块放回空闲列表并合并——同一块放两次，空闲列表出现重复节点，堆记账损坏，通常直接崩溃。更常见的形态是**两个指针指向同一块，各自都以为自己该释放**：

```cpp
int* a = new int(1);
int* b = a;          // 两个指针，一块内存——"谁负责释放"从此说不清
delete a;
delete b;            // 反例，勿模仿！double free
```

记住这个形态，第 7 节推导「unique_ptr 为什么禁止拷贝」时它会再次登场。

**（4）new/delete 形式不匹配**：上一节已经从 cookie 机制推导过了——`new[]` 配 `delete`、`new` 配 `delete[]`、或者和 `malloc`/`free` 交叉，都是记账系统层面的 UB。

### 3.2 共同根源：退出路径爆炸

四类事故里，(1) 和它的隐蔽版本暴露了问题的本质。来做个推演。

假设一个函数先后获取 3 个资源，中间有 4 处可能提前退出（参数检查失败、某步出错……）。手动配对意味着：

- **每一个退出点**，都要释放「到这里为止已经获取的所有资源」；
- 而且要**倒序**释放（后获取的可能依赖先获取的）；
- 每加一个分支、挪一行获取代码，**所有退出点都要重新检查一遍**。

释放代码的份数 ≈ 退出点数 × 平均已持有资源数，随着函数变长呈乘性增长。你在 C 里见过对付它的最好办法——`goto cleanup`（Linux 内核到处都是）：

```c
int process(void) {
    int ret = -1;
    FILE* f = fopen("a.txt", "r");
    if (!f) goto out;
    char* buf = malloc(4096);
    if (!buf) goto close_file;
    /* ... 干活，出错就 goto free_buf ... */
    ret = 0;
free_buf:
    free(buf);
close_file:
    fclose(f);
out:
    return ret;
}
```

这个模式的思路是对的：**把多个退出点收敛成一条统一的清理路径**。但它有两个致命局限：

1. 它仍然是「纪律」不是「保证」——标签顺序写错、某个分支忘了 goto，编译器不会拦你；
2. 在 C++ 里它**彻底失效**：异常让**任何一行**都可能成为隐形退出点（一个函数调用、甚至一个 `new` 都可能抛），你根本没法在「每个退出点」写 goto，因为你不知道退出点在哪。

推演到这里，结论只剩一个：靠人在每条退出路径上补释放代码，此路不通。唯一可靠的方案是——**把「释放」挂到一个无论以哪条路径离开、都必然发生的事件上**。

C 里没有这样的事件。C++ 里有。

## 4. 语言级保证：析构一定会被调用

上一节要找一个「无论怎么离开作用域都必然发生的事件」。它就是**栈对象的析构**。这不是一个「通常会发生」的行为，而是 C++ 标准规定、编译器负责兑现的**语言级保证**。RAII 的整座大厦都盖在这一节上，所以值得把「必然」二字掰开：离开作用域一共三条路径，逐条看编译器怎么兑现。

### 4.1 路径一：正常走到作用域结尾

还记得 1.1 节留的那句话吗——**编译器精确知道每个局部变量在哪个作用域结束**。所以它能在 `}` 之前，为每个局部对象**生成析构调用指令**，顺序与构造相反（后构造的先析构，因为后者可能依赖前者）。析构调用是编译进代码里的，跟你手写在那里没区别——只是你不用写。

### 4.2 路径二：提前 return / break / continue

作用域可能有多个出口。编译器在**每一个出口**都插入析构调用（实现上通常是各出口跳到统一的清理代码——就是 3.2 节那个 `goto cleanup` 模式，只不过这次是编译器自动生成的，不会漏、不会错序）。你手动配对时最容易漏的「提前 return」，在这里被机器穷举覆盖了。

### 4.3 路径三：异常栈展开

函数抛出异常时，运行时会做**栈展开**（stack unwinding）：从抛出点开始逐层退出栈帧，每退一层，**调用该帧里所有已构造完成的局部对象的析构函数**，直到找到能接住异常的 `catch`。这就是为什么 MSVC 编译要带 `/EHsc`——告诉编译器生成支持栈展开的异常处理代码。

3.2 节说异常让「任何一行都可能是隐形退出点」，goto 模式因此失效——而栈展开恰恰把这些隐形退出点也全覆盖了。

三条路径合成一个可运行的验证：

```cpp
#include <cstdio>
#include <stdexcept>

struct Tracer {
    const char* name;
    explicit Tracer(const char* n) : name(n) { std::printf("%s 构造\n", name); }
    ~Tracer() { std::printf("%s 析构\n", name); }
};

void path1_normal() {
    Tracer t("路径1-正常走完");
}                                    // } 前编译器插入了 t.~Tracer()

void path2_early(bool cond) {
    Tracer t("路径2-提前return");
    if (cond) return;                // 这个出口同样插了 t.~Tracer()
    std::puts("走不到这");
}

void path3_throw() {
    Tracer t("路径3-异常");
    throw std::runtime_error("出错了");   // 栈展开时调用 t.~Tracer()
}

int main() {
    path1_normal();
    path2_early(true);
    try {
        path3_throw();
    } catch (const std::exception& e) {
        std::printf("捕获异常: %s\n", e.what());   // 在这之前，t 已经析构完了
    }
}
```

跑一下：三条路径，三次「析构」打印，一次不少。

### 4.4 边界说清楚：保证的范围

严谨起见，这条保证的适用范围是「**控制流离开了作用域**」。有几种情况控制流根本没走离开作用域这条路，析构自然不发生：`std::abort()`、`std::exit()`（跳过栈上局部对象的析构）、异常一路没人接导致 `std::terminate`。这些都是「程序整个放弃治疗」的场景，不影响正常程序里的结论：

**只要函数还在正常的控制流里，栈对象的析构就一定执行。** 这就是第 3 节要找的那个「必然发生的事件」。剩下的事情顺理成章：把释放动作搬进去。

---

## 5. RAII：把资源绑到这条保证上

钩子找到了，现在挂东西。思路一句话：**资源的「获取」放进构造函数，「释放」放进析构函数，让资源的生命周期等于对象的生命周期。** 这个手法叫 RAII——Resource Acquisition Is Initialization，资源获取即初始化。名字确实拗口，你可以按机制记它：**析构即释放**。

### 5.1 从 C 的痛到 C++ 的解

C 里管理一个文件：

```c
FILE* fp = fopen("data.txt", "r");   /* 获取 */
if (!fp) return;
/* ... 中间每一条 return、每一处出错分支，都得记得 fclose ... */
fclose(fp);                          /* 释放：人肉保证每条路径都有 */
```

C++ 里把 `FILE*` 包进类，获取进构造、释放进析构：

```cpp
#include <cstdio>

class File {
public:
    File(const char* path, const char* mode)
        : fp_(std::fopen(path, mode)) {}          // 获取：构造时打开
    ~File() {
        if (fp_) std::fclose(fp_);                // 释放：析构时关闭
    }

    File(const File&) = delete;                   // 禁止拷贝，5.3 推导为什么
    File& operator=(const File&) = delete;

    bool valid() const { return fp_ != nullptr; }
    std::FILE* get() const { return fp_; }

private:
    std::FILE* fp_;
};

void process(bool something) {
    File f("data.txt", "w");
    if (!f.valid()) return;          // 打开失败提前走：fp_ 为空，析构里 if 挡住
    if (something) return;           // 提前返回：f 析构 → 自动 fclose
    std::fputs("hello\n", f.get());  // 就算这里抛异常：栈展开 → f 析构 → fclose
}                                    // 正常走完：f 析构 → fclose
```

对比一下发生了什么质变：

| | C 手动配对 | C++ RAII |
|---|---|---|
| 释放代码写几遍 | 每条退出路径一遍 | **构造/析构里各一遍，共一遍** |
| 提前 return | 每处手动补 | 自动覆盖（4.2 的保证） |
| 抛异常 | 无解（C 没异常，C++ 里 goto 模式失效） | 自动覆盖（4.3 的栈展开） |
| 谁保证正确 | 程序员的纪律 | 编译器生成的代码 |

第 3 节的「退出路径爆炸”问题，就这样被结构性地消灭了：不管有多少条退出路径，释放逻辑只存在一份，而且由第 4 节那条语言保证兜底，**每条路径都必然经过它**。异常安全不是额外争取来的特性，是白送的。

### 5.2 推导：资源类为什么必须禁止拷贝

上面 `File` 里那两行 `= delete` 不是习惯用法，是推导出来的必然。假设不禁：

编译器默认生成的拷贝构造是**逐成员拷贝**——拷贝一个 `File`，就是拷贝那个 `fp_` 指针。于是两个 `File` 对象持有**同一个** `FILE*`。两个对象先后析构，`fclose` 同一个句柄调两次——这就是 3.1 节事故 (3)「两个指针指向同一块，各自都以为自己该释放」的翻版，double close。

所以规则是从机制来的：**只要类的析构会释放资源，默认拷贝就是错的**，要么禁止（`= delete`），要么自己定义拷贝该是什么意思（比如深拷贝）。「那想把资源转手给别人怎么办？」——好问题，答案叫**移动**，第 7 节见雏形，完整故事在 M5。

mini 项目里的 `raii_file.cpp` 练的就是这一整节：封装 FILE*、禁拷贝、想清楚为什么。

### 5.3 你其实早就在用 RAII

标准库里所有管理资源的类型都是 RAII：`std::string`（管字符缓冲区）、`std::vector`（管动态数组）、`std::fstream`（管文件）、`std::lock_guard`（管锁）。你在 M2 写的 `FileWrapper` 就是亲手写的第一个 RAII 类。日常开发里你很少需要自己写 RAII 类——但有一种资源太常用了，标准库为它做了专门的、泛化的 RAII 封装。往下看。

## 6. 把 RAII 泛化成类型：智能指针总览

RAII 解决了「怎么自动释放」。但按第 5 节的写法，每种资源都要写一个包装类：管 `FILE*` 写一个、管堆上的 `Widget` 写一个、管 `Texture` 再写一个……而其中「堆内存」是最高频的资源，包装逻辑又高度雷同：持有一个指针、析构时 delete、禁止拷贝。

雷同的逻辑就该抽成模板。标准库在 `<memory>` 里提供的**智能指针**，本质就是「裸指针的 RAII 包装」做成的类模板——长得像指针（重载了 `*` 和 `->`），行为上把「谁负责 delete」这件事编码进了**类型**里。

C++17 常用三种，区别只在**所有权语义**：

| 智能指针 | 所有权 | 能否拷贝 | 典型场景 |
|---|---|---|---|
| `std::unique_ptr` | 独占（唯一拥有者） | 不可拷贝，可移动 | **默认首选**，绝大多数场景 |
| `std::shared_ptr` | 共享（引用计数） | 可拷贝 | 确实没有唯一拥有者时 |
| `std::weak_ptr` | 不拥有（观察者） | 可拷贝 | 打破 shared_ptr 循环引用 |

心法：**先问「这块内存谁拥有」，答案决定类型。** 接下来三节按「所有权从简单到复杂」的顺序讲：独占（第 7 节）→ 共享（第 8 节）→ 观察（第 9 节），每一种都讲到内存布局层面。

## 7. `unique_ptr`：独占所有权，零开销

独占是最简单也最常见的所有权关系：一块内存，一个拥有者，拥有者死，内存亡。`unique_ptr` 表达的就是它。

### 7.1 它本质是什么——手写一个就全明白了

`unique_ptr` 没有任何魔法。它本质就是三样东西：**一个裸指针 + 析构函数里 delete + 禁止拷贝**。外加移动支持，一个能用的简化版长这样（这也是 mini 项目 `my_unique_ptr.cpp` 的地图）：

```cpp
#include <cstdio>
#include <utility>   // std::move

template <typename T>
class UniquePtr {
public:
    explicit UniquePtr(T* p = nullptr) : ptr_(p) {}
    ~UniquePtr() { delete ptr_; }                    // RAII：析构即释放
                                                     // (delete nullptr 是安全的空操作)
    UniquePtr(const UniquePtr&) = delete;            // 独占：禁止拷贝（7.2 推导）
    UniquePtr& operator=(const UniquePtr&) = delete;

    UniquePtr(UniquePtr&& other) noexcept            // 移动构造：把指针"偷"过来
        : ptr_(other.ptr_) {
        other.ptr_ = nullptr;                        // 源方置空——所有权只有一份
    }
    UniquePtr& operator=(UniquePtr&& other) noexcept {
        if (this != &other) {                        // 防自我移动
            delete ptr_;                             // 先放掉自己原来管的
            ptr_ = other.ptr_;                       // 再接管对方的
            other.ptr_ = nullptr;
        }
        return *this;
    }

    T& operator*() const { return *ptr_; }           // 让它用起来像指针
    T* operator->() const { return ptr_; }
    T* get() const { return ptr_; }
    explicit operator bool() const { return ptr_ != nullptr; }

private:
    T* ptr_;                                         // 全部数据成员：就一个裸指针
};

struct Res {
    Res()  { std::puts("Res 构造"); }
    ~Res() { std::puts("Res 析构"); }
    void hi() { std::puts("hi"); }
};

int main() {
    UniquePtr<Res> a(new Res);
    a->hi();
    UniquePtr<Res> b(std::move(a));   // 所有权 a → b
    if (!a) std::puts("a 已空");
}   // b 析构 → delete → "Res 析构"。全程没手写 delete
```

### 7.2 推导：独占为什么必须禁止拷贝

假设允许拷贝。默认拷贝是逐成员的，拷贝一个 `UniquePtr` 就是拷贝 `ptr_`：

```
UniquePtr a  ──ptr_──┐
                     ├──→ 同一个 Res
UniquePtr b  ──ptr_──┘   （b 从 a 拷贝而来）

a 析构：delete ptr_   →  Res 没了
b 析构：delete ptr_   →  对同一地址第二次 delete —— double free
```

这正是 3.1 节事故 (3) 和 5.2 节 double close 的同一个错误，第三次出现——**「两个拥有者」和「独占」在逻辑上就是矛盾的**。`unique_ptr` 的做法是把这个矛盾从「运行期崩溃」提前成「编译期报错」：

```cpp
auto a = std::make_unique<Res>();
auto b = a;              // 编译错误！拷贝构造是 delete 的
auto c = std::move(a);   // OK：转移。所有权给 c，a 变成 nullptr
```

体会一下这里的质变：C 里「两个指针指向一块内存」是合法代码 + 运行期地雷；C++ 里用类型把这种状态**直接变成写不出来的代码**。这就是「用类型表达所有权」的含金量。

至于 `std::move`——此刻你只需要知道它是「我自愿交出所有权」的显式声明，转移后源指针为空。它背后到底发生了什么、为什么资源类都该支持移动，是 **M5 的核心主线**，这里埋个伏笔。

### 7.3 零开销：为什么「不用白不用」

对照 7.1 的实现算一笔账：

- **空间**：唯一的数据成员是一个裸指针，所以 `sizeof(unique_ptr<T>)（默认删除器）== sizeof(T*)`，8 字节。没有计数、没有额外堆块。
- **时间**：析构函数就一句 `delete ptr_`，编译器内联后，生成的机器码和你手写「裸指针 + 每条路径 delete」**完全一样**——只是那些 delete 由编译器按第 4 节的保证替你插在每个出口。

结论：`unique_ptr` 相比手动管理的裸指针，运行期开销为零，安全性从「靠纪律」变成「靠编译器」。这就是为什么它是**默认选择**——不存在「为了性能用裸指针管理所有权」的理由。

### 7.4 日常用法

创建，优先用 `std::make_unique`（C++14 起）：

```cpp
auto p = std::make_unique<Widget>(42);      // 推荐
std::unique_ptr<Widget> q(new Widget(42));  // 能用，但不如上面
```

`make_unique` 的好处：代码里**看不到裸 new**，不存在「new 完还没交给智能指针的窗口期」（窗口期里抛异常就泄漏）；类型也只写一遍。

常用操作：

```cpp
auto p = std::make_unique<int>(5);
int* raw = p.get();      // 借出裸指针给别人"看"——对方绝不能 delete
p.reset();               // 提前释放，p 变 nullptr
p.reset(new int(9));     // 释放旧的，接管新的
int* r = p.release();    // 放弃所有权，返回裸指针——释放责任回到你手上！
delete r;                // release 后你就是"手动管理"了，忘了 delete 就泄漏
if (p) { /* 判空 */ }
```

注意 `get()` 和 `release()` 的本质区别：`get` 是**借用**（所有权还在 p），`release` 是**弃权**（p 从此不管了）。

### 7.5 工厂函数：unique_ptr 最漂亮的用法

第 1.3 节说堆的一个刚需是「对象生命周期超出创建它的作用域」——工厂函数正是这个场景，而 `unique_ptr` 把它做得又安全又零开销：

```cpp
#include <cstdio>
#include <memory>

struct Shape {
    virtual double area() const = 0;
    virtual ~Shape() = default;        // 虚析构！M3 的老朋友，下面解释为什么必须
};

struct Circle : Shape {
    double r;
    explicit Circle(double rr) : r(rr) {}
    double area() const override { return 3.14159 * r * r; }
    ~Circle() override { std::puts("Circle 析构"); }
};

std::unique_ptr<Shape> makeShape(double r) {
    return std::make_unique<Circle>(r);    // 所有权直接交给调用者
}

int main() {
    auto s = makeShape(2.0);               // s 拥有这个 Circle
    std::printf("面积 = %.2f\n", s->area());
}   // s 析构 → 通过 Shape* delete → 因为虚析构，正确调到 ~Circle
```

这里 M3 的知识直接接上了：`unique_ptr<Shape>` 析构时是**通过基类指针 delete 派生类对象**——基类没有虚析构的话，只会调 `~Shape`，`Circle` 部分的清理全跳过，UB + 泄漏。**凡是会被 `unique_ptr<Base>` / `shared_ptr<Base>` 管理的多态基类，必须有虚析构**。练习 6 练的就是这套组合。

## 8. `shared_ptr`：共享所有权与控制块

`unique_ptr` 的前提是「存在唯一拥有者」。但有的场景这个前提不成立：一块数据被多个模块引用，**谁都可能是最后一个用完的**，而「谁是最后一个」要到运行期才知道。独占模型表达不了这种关系——你需要计数：记录还有几个拥有者，最后一个离开的人负责关灯。这就是 `shared_ptr`。

### 8.1 内存里到底有几块东西

这是理解 `shared_ptr` 的关键，先画图。一个 `shared_ptr` 对象内部有**两个指针**（所以 `sizeof(shared_ptr) == 2 × sizeof(void*)`，16 字节，比 unique_ptr 大一倍），分别指向堆上的两样东西：

```
栈上                          堆上
┌─────────────────┐
│ shared_ptr a    │        ┌─────────────────┐
│   对象指针 ──────┼───────→ │   Widget 对象    │
│   控制块指针 ────┼───┐    └─────────────────┘
└─────────────────┘   │    ┌─────────────────┐
                      └───→ │     控制块       │
┌─────────────────┐   ┌───→ │  强计数 = 2      │ ← 几个 shared_ptr 拥有对象
│ shared_ptr b    │   │    │  弱计数 = 0      │ ← 几个 weak_ptr 在观察(第9节)
│   对象指针 ──────┼──…│    │  删除器等        │ ← 怎么释放对象(第10节)
│   控制块指针 ────┼───┘    └─────────────────┘
└─────────────────┘
  (b 是 a 的拷贝，两个指针都指向同一处)
```

**控制块**（control block）是所有指向同一对象的 `shared_ptr` 共享的「记账中心」。计数的变化规则很机械：

- 拷贝一个 `shared_ptr` → 强计数 +1；
- 一个 `shared_ptr` 析构（或 reset）→ 强计数 −1；
- **强计数减到 0 → 调用对象的析构、释放对象**。

跑一遍验证：

```cpp
#include <cstdio>
#include <memory>

struct Res {
    Res()  { std::puts("Res 构造"); }
    ~Res() { std::puts("Res 析构"); }
};

int main() {
    auto a = std::make_shared<Res>();                  // 强计数 = 1
    std::printf("计数 = %ld\n", (long)a.use_count());  // 1
    {
        auto b = a;                                    // 拷贝：强计数 = 2
        std::printf("计数 = %ld\n", (long)a.use_count());
    }                                                  // b 析构：强计数 = 1，对象还活着
    std::printf("计数 = %ld\n", (long)a.use_count());  // 1
}   // a 析构：强计数 = 0 → 这时才打印 "Res 析构"
```

### 8.2 make_shared vs shared_ptr(new T)：一次分配 vs 两次

创建方式有两种，内存布局不一样，画出来一目了然：

```
方式一：std::shared_ptr<T> p(new T);      —— 两次堆分配
   分配 #1: ┌─────────┐      分配 #2: ┌─────────┐
            │  T 对象  │               │  控制块  │
            └─────────┘               └─────────┘
   (你 new 了对象，shared_ptr 构造时发现没有控制块，只好再分配一个)

方式二：auto p = std::make_shared<T>();   —— 一次堆分配
            ┌─────────┬─────────┐
            │  控制块  │  T 对象  │      ← 一块连续内存装下两样
            └─────────┴─────────┘
```

`make_shared` 的好处（高频面试点，要点都在上图里）：
1. **一次分配**：第 1 节讲过每次堆分配都要查空闲列表、记账、可能加锁——省一次就是实打实的性能；两样东西挨着，缓存也更友好。
2. **异常安全**：没有裸 `new` 暴露在外，不存在「对象 new 好了、还没交给 shared_ptr 就抛异常」的泄漏窗口。
3. 代码短，类型只写一遍。

（这个合并布局有一个微妙的代价，和 `weak_ptr` 有关，放到 9.4 讲——那时你才有背景理解它。）

### 8.3 计数为什么必须是原子操作，代价是什么

多个线程可以各自持有指向同一对象的 `shared_ptr` 拷贝，并且随时拷贝/销毁自己那份——也就是说，**多个线程会并发地对同一个控制块做 +1/−1**。普通的 `++` 是「读-改-写」三步，两个线程交错执行会丢更新：计数错了，轻则泄漏（多算），重则提前释放 + double free（少算）。所以标准要求计数操作是**原子的**。

原子操作的代价：它要用带锁前缀的指令、要在核心间同步缓存行，比普通自增慢一个数量级；多线程频繁拷贝同一个 `shared_ptr` 指向的对象时，各核心还会争抢控制块所在的缓存行。加上多出的控制块内存和两倍的指针大小，结论就出来了：

> **`shared_ptr` 不是「更高级的 unique_ptr」，是「更贵的、语义不同的指针」。** 能用 `unique_ptr` 就用 `unique_ptr`，确实存在多个拥有者时才上 `shared_ptr`。

顺带把「shared_ptr 线程安全吗」这个高频问题的准确答案立在这（机制刚讲完，正好）：
- **控制块的计数操作是线程安全的**：不同线程操作「指向同一对象的**不同** shared_ptr 实例」（各自拷贝、各自析构），安全。
- **它指向的对象不是自动线程安全的**：多线程读写 Widget 本身，该加锁还得加锁。
- **同一个 shared_ptr 实例**被多线程同时修改（比如同时 reset），不安全。

## 9. 循环引用与 `weak_ptr`

引用计数的规则简单机械：拷贝 +1、析构 −1、归零释放。但机械正是它的弱点——**它只数「有几个人拿着」，不理解「拿着的人自己是不是永远不会松手」**。这一节先推演出这个弱点怎么变成泄漏，再看标准库怎么修。

### 9.1 推演一次泄漏：计数为什么停在 1

两个节点用 `shared_ptr` 互相指着对方：

```cpp
#include <cstdio>
#include <memory>

struct BadNode {
    std::shared_ptr<BadNode> next;
    std::shared_ptr<BadNode> prev;
    ~BadNode() { std::puts("BadNode 析构"); }
};

void leak() {
    auto a = std::make_shared<BadNode>();   // 节点A 强计数=1 (a)
    auto b = std::make_shared<BadNode>();   // 节点B 强计数=1 (b)
    a->next = b;                            // 节点B 强计数=2 (b, A.next)
    b->prev = a;                            // 节点A 强计数=2 (a, B.prev)
}
// 离开作用域，逐步算：
//   栈变量 b 析构 → 节点B 计数 2→1（A.next 还拿着它）
//   栈变量 a 析构 → 节点A 计数 2→1（B.prev 还拿着它）
//   然后……就没有然后了。看不到任何 "BadNode 析构"。
```

为什么停在 1 就再也降不下去？把依赖链写出来：

```
节点A 计数要归 0  ← 需要 B.prev 析构  ← 需要 节点B 被析构
                                            ↑
节点B 计数要归 0  ← 需要 A.next 析构  ← 需要 节点A 被析构
```

A 的释放等 B，B 的释放等 A——一个谁也不肯先松手的死锁。栈上的入口没了，堆上两个节点互相攥着，程序再也够不到它们：泄漏。注意这**不是 shared_ptr 的 bug**，计数每一步都算对了；是「互相拥有」这个所有权设计本身就是矛盾的。

### 9.2 修复：把「指回去」的那条边改成不拥有

解药是承认一件事：双向关系里，两个方向的语义**本来就不对等**——「父拥有子」是拥有，「子指回父」只是想找到父，不该拥有。表达「引用但不拥有」的类型就是 `weak_ptr`：它指向 shared_ptr 管理的对象，但**不增加强计数**。

```cpp
#include <cstdio>
#include <memory>

struct GoodNode {
    std::shared_ptr<GoodNode> next;   // 拥有下一个
    std::weak_ptr<GoodNode>   prev;   // 指回上一个，但不拥有
    ~GoodNode() { std::puts("GoodNode 析构"); }
};

void fixed() {
    auto a = std::make_shared<GoodNode>();  // 节点A 强计数=1
    auto b = std::make_shared<GoodNode>();  // 节点B 强计数=1
    a->next = b;                            // 节点B 强计数=2
    b->prev = a;                            // weak_ptr：节点A 强计数仍=1！
}
// 离开作用域，再逐步算：
//   b 析构 → 节点B 计数 2→1
//   a 析构 → 节点A 计数 1→0 → 节点A 析构！
//     → A.next 随之析构 → 节点B 计数 1→0 → 节点B 析构！
// 两声 "GoodNode 析构"，全部释放。

int main() { fixed(); }
```

对比 9.1 的推演：weak 边不参与计数，依赖链断了一环，多米诺就能倒下去。

### 9.3 lock()：为什么它能安全判断对象还活不活着

`weak_ptr` 不拥有对象，意味着**它指着的对象随时可能没了**，所以它故意不提供 `*` 和 `->`。用之前必须先「升级」：

```cpp
std::weak_ptr<GoodNode> w = /* 某个 shared_ptr */;
if (auto sp = w.lock()) {      // 对象还活着 → 返回有效 shared_ptr（计数+1，锁定生命）
    // 在 sp 的作用域里，对象保证活着
} else {
    // 对象已经析构了
}
```

这里有个值得深究的问题：对象都可能没了，`lock()` 去哪查「活着没有」？答案回到 8.1 的控制块——**控制块比对象活得久**。完整的生命周期规则是：

```
强计数 → 0：析构并释放"对象"      （但控制块还在！）
强计数和弱计数都 → 0：释放"控制块"
```

`weak_ptr` 持有的是控制块指针，并把弱计数 +1，等于说：「对象你们该释放就释放，但**记账本给我留着**」。`lock()` 做的事是一个原子操作：「查强计数，>0 就 +1 并返回 shared_ptr，==0 就返回空」。原子性很关键——查和加是一步完成的，不存在「刚查完还活着、拿到手对象却没了」的间隙。

这也顺便解释了为什么悬垂裸指针无药可救而 `weak_ptr` 能自救：裸指针只有一个地址，指向的内存没了它毫不知情；`weak_ptr` 手里多攥着一本活账。

### 9.4 现在能理解 make_shared 的那个权衡了

8.2 留了个尾巴。`make_shared` 把对象和控制块放进**同一块**分配的内存——而刚才说了，只要还有 `weak_ptr` 活着，控制块就不能释放。同一块内存不能拆开还一半，于是：**只要有 weak_ptr 存活，对象占的那部分内存也一起被拖着不能还给分配器**（对象本身已析构，占着的只是内存）。对象很大、weak_ptr 又长寿的场景要留意；绝大多数情况无所谓，仍然优先 `make_shared`。

### 9.5 经验法则

**表达「拥有」用 `shared_ptr`，表达「指回去 / 观察者 / 缓存」用 `weak_ptr`。** 父子、双向链表、观察者模式这类结构：拥有方向用 shared，回指方向用 weak。练习 8 会让你把泄漏和修复各跑一遍，亲眼看析构打印的有无。

## 10. 自定义删除器：智能指针管理任意资源

到这里智能指针管的都是「`new` 出来、该用 `delete` 释放」的内存。但第 5 节的 RAII 是对**一切资源**说的——`FILE*` 要 `fclose`，C 库句柄要专门的销毁函数。智能指针能不能管它们？能：释放动作本来就是智能指针的一个可替换零件，叫**删除器**（deleter）。

```cpp
#include <cstdio>
#include <memory>

int main() {
    // unique_ptr：删除器是模板参数的一部分（进类型）
    auto closer = [](std::FILE* f) { if (f) std::fclose(f); };
    std::unique_ptr<std::FILE, decltype(closer)> fp(std::fopen("data.txt", "r"), closer);
    if (fp) std::puts("打开成功，离开作用域自动 fclose");

    // shared_ptr：删除器只在构造时传，不进类型
    std::shared_ptr<std::FILE> sp(std::fopen("x.txt", "r"),
                                  [](std::FILE* f) { if (f) std::fclose(f); });
}
```

注意两者的结构性差别，而且你已经有背景理解它了：

- `unique_ptr<FILE, D>` 把删除器放进**类型**——无状态的 lambda 不占空间，7.3 的零开销得以保持；代价是删除器不同的 unique_ptr 是不同类型。
- `shared_ptr<FILE>` 把删除器存进**控制块**（8.1 图里那格「删除器等」就是它）——反正控制块已经存在了，捎带一个删除器不增加 shared_ptr 本身的大小，删除器不同也不影响类型。

实战里封装 C 库（音视频方向的 FFmpeg 满地都是 `av_xxx_free` 型句柄）时这招非常常用。mini 项目的 `raii_file.cpp` 你可以手写 `FileGuard` 类，也可以体会一下删除器版本，两种思路殊途同归：**都是把释放绑到析构上**。

## 11. 所有权思维：让函数签名说话

机制到齐了，最后把它们收束成一套设计语言。内存管理的一切归结为一个问题：**这块资源谁拥有？** 而 C++ 的智能指针让你能把答案写进类型，让编译器帮你审查。

两个核心概念：

- **拥有（owning）**：我对它的生命周期负责，我消失时它该被释放（或计数减一）。用智能指针表达。
- **借用（non-owning）**：我只是用一下，用完就走，绝不释放。用引用或裸指针表达。

函数签名因此获得了表达力——参数类型就是所有权契约：

```cpp
#include <cstdio>
#include <memory>

struct Widget { int v = 7; };

// 借用：只是用一下，不碰所有权。调用后原对象还在原地。
void observe(const Widget& w) { std::printf("看一眼: %d\n", w.v); }

// 借用但可能为空：用裸指针（现代 C++ 裸指针的唯一角色）
void maybeObserve(const Widget* w) { if (w) std::printf("看一眼: %d\n", w->v); }

// 接管：按值收 unique_ptr。调用者必须 std::move 进来，明示"给你了"
void take(std::unique_ptr<Widget> w) { std::printf("接管: %d\n", w->v); }
// w 在这里析构 → Widget 随之释放：接管方负责到底

// 入伙：按值收 shared_ptr，计数 +1，共同拥有
void share(std::shared_ptr<Widget> w) { std::printf("计数: %ld\n", (long)w.use_count()); }

int main() {
    auto u = std::make_unique<Widget>();
    observe(*u);              // 借用：u 的所有权纹丝不动
    maybeObserve(u.get());    // 借用：get() 交出的是"参观券"不是"房产证"
    take(std::move(u));       // 转移：从此 u 为空，Widget 归 take 处置
    auto s = std::make_shared<Widget>();
    share(s);                 // 共享：函数内计数是 2，返回后回到 1
}
```

传参贴士（新手最常见的滥用）：**只是用一下对象，就传引用/裸指针，别传智能指针。** `void f(const shared_ptr<Widget>&)` 这种签名，既没转移也没共享，却强迫调用者必须持有 shared_ptr——想传个栈对象、unique_ptr 管的对象都不行。所有权不相关时，参数就写 `const Widget&`。

### 何时用哪种：决策速查

| 情况 | 用什么 |
|---|---|
| 对象能放栈上、生命周期不超出作用域 | **栈对象**，别上堆（第 1 节：最快最安全） |
| 堆对象，单一拥有者（绝大多数情况） | `std::unique_ptr`（第 7 节：零开销） |
| 堆对象，真的多个拥有者、谁后用完不确定 | `std::shared_ptr`（第 8 节：有代价） |
| shared 结构里的回指边 / 观察者 | `std::weak_ptr`（第 9 节） |
| 只借用，不拥有 | `T&`，可空则 `T*` |
| 动态数组 | `std::vector`（首选，M6 见）或 `make_unique<T[]>(n)` |

决策从上往下问：能上栈吗 → 有唯一拥有者吗 → 真的需要共享吗。**裸指针在现代 C++ 里没有消失，但角色变了：它只表示「借用」，永远不表示「拥有」。** 看到函数返回裸指针，读作「借你看看」；看到返回 unique_ptr，读作「归你了」。代码变成了自我说明的所有权文档。

顺带把开头那句话闭环：现代 C++ 的准则「几乎不再手写 `new`/`delete`」不是风格洁癖，是推导的终点——`new` 被 `make_unique`/`make_shared` 包掉（7.4/8.2 的异常安全窗口），`delete` 被析构函数包掉（第 4、5 节的语言保证）。裸的 new/delete 没有存在的必要了。

## 12. 常见坑

九个坑，每个都能用前面的机制解释——标了对应小节，忘了原理就翻回去。

1. **`new`/`delete` 与 `new[]`/`delete[]` 混用** → UB。cookie 记账对不上（2.3 的推导），且对 int 这类类型经常「碰巧不炸」，更阴险。
2. **`new` 的内存用 `free`、`malloc` 的用 `delete`** → UB。跳过构造/析构 + 可能是两套记账系统（2.2 的推导）。
3. **同一个裸指针交给两个智能指针**：
   ```cpp
   Widget* raw = new Widget;
   std::shared_ptr<Widget> a(raw);
   std::shared_ptr<Widget> b(raw);   // 反例，勿模仿！
   ```
   从裸指针构造 shared_ptr 会**新建控制块**（8.1）——a、b 各有一个控制块、各自计数为 1，互不知情，先后归零就是 double free。正确做法：`make_shared`，或 `auto b = a;`（拷贝才共享控制块）。
4. **用裸指针接管临时智能指针的对象**：
   ```cpp
   Widget* raw = std::make_unique<Widget>().get();   // 反例，勿模仿！
   ```
   临时 unique_ptr 这一行结束就析构（第 4 节的保证反过来咬你），raw 当场悬垂。
5. **把栈对象地址塞进智能指针**：
   ```cpp
   Widget w;
   std::unique_ptr<Widget> p(&w);   // 反例，勿模仿！
   ```
   p 析构时会 `delete` 一个不是 `operator new` 分配的地址——分配器找不到对应块头（1.2），崩溃。智能指针默认删除器只能接管 `new` 出来的内存。
6. **shared_ptr 循环引用** → 计数停在 1，永不归零（9.1 的推演）。回指边改 `weak_ptr`。
7. **`release()` 后忘记 delete**：`release` 是弃权不是释放（7.4），责任回到你手上。只想看一眼用 `get()`。
8. **无脑用 shared_ptr**：原子计数 + 控制块 + 双倍指针大小都是真实代价（8.3）。默认 `unique_ptr`。
9. **手动管理时 `delete` 后不置空** → 悬垂误用。`delete p; p = nullptr;` 是 C 时代的自保习惯；用智能指针后这个问题整体消失（reset 自动置空）。

## 13. 高频面试点

- **`new`/`delete` 和 `malloc`/`free` 的区别？**
  要点：new = 分配 + 调构造，delete = 调析构 + 释放，malloc/free 只管内存；类型安全（不用强转/sizeof）；失败处理（bad_alloc vs NULL）。加分项：能说出 operator new / placement new 的两步分解（2.1）。
- **`delete` 和 `delete[]` 的区别？为什么不能混用？**
  要点：delete[] 依赖 new[] 埋的 cookie 得知元素个数、逐个析构、按真实分配起点释放；用错则析构次数错 + 释放地址错，UB（2.3）。
- **`unique_ptr` 和 `shared_ptr` 的区别？**
  要点：独占 vs 共享；不可拷贝只可移动 vs 可拷贝引用计数；零开销（sizeof 一个裸指针、无控制块）vs 有代价（控制块 + 原子计数 + 双指针大小）。默认选 unique_ptr。
- **`unique_ptr` 为什么不能拷贝？**
  要点：拷贝 = 两个拥有者 = 析构时对同一指针 delete 两次（7.2 推导）；`= delete` 拷贝把运行期 double free 变成编译错误；转移所有权用 std::move。
- **什么是 RAII？**
  要点：获取放构造、释放放析构，资源生命周期 = 对象生命周期；依赖「析构必被调用」的语言保证（正常离开/提前 return/异常栈展开三条路径）；因此天然异常安全。举例：lock_guard、fstream、智能指针。
- **`make_shared` 相比 `shared_ptr(new T)` 的好处？**
  要点：一次分配合并对象与控制块（省一次堆记账、缓存友好）；无裸 new 的异常安全窗口；权衡：weak_ptr 存活时对象内存跟着控制块一起不能释放（9.4）。
- **`shared_ptr` 是线程安全的吗？**
  要点分三层：计数操作是原子的，多线程操作不同实例安全；被管理的对象本身不自动线程安全；同一实例被多线程同时修改不安全（8.3）。
- **什么是循环引用？怎么解决？**
  要点：两个对象经 shared_ptr 互指，各自计数只能降到 1（能推演计数变化最好，9.1）；把「回指/不拥有」的边改成 weak_ptr。
- **`weak_ptr` 的原理？`lock()` 为什么安全？**
  要点：持控制块指针、加弱计数、不加强计数；控制块比对象活得久（强计数 0 析构对象，双计数 0 才释放控制块）；lock 原子地「强计数 >0 则 +1 并返回 shared_ptr，否则返回空」（9.3）。
- **智能指针在哪个头文件？** `<memory>`。

## 15. 与相邻模块的呼应

- **回顾 M2**：M2 建立了「析构 = 自动清理」的直觉，你写的 `FileWrapper`（构造 fopen、析构 fclose）就是第一个 RAII 类。M4 把这个直觉的地基挖开给你看了：它成立是因为「析构必被调用」是语言级保证（第 4 节），而且这条保证覆盖异常路径——这是当时没讲的部分。
- **回顾 M3**：多态基类要 `virtual ~Base()`。M4 里它落地成了硬规则：`unique_ptr<Base>`/`shared_ptr<Base>` 管理派生类对象时，析构走的正是「通过基类指针 delete」这条路（7.5），没有虚析构就是不完整析构 + UB。
- **伏笔 M5**：本模块两处埋了同一根线——`unique_ptr` 不可拷贝只可移动（7.2），资源类默认拷贝是错的、想「转手」需要移动（5.2）。**「拷贝一个对象到底发生什么、移动到底偷走了什么、什么时候该自己写拷贝/移动函数（Rule of 0/3/5）」就是 M5 的核心。** 你在 mini 项目里手写的移动构造/移动赋值（偷指针、置空源、防自赋值），正是 M5 要系统化的那套东西——先动手写一遍，M5 讲原理时你会非常有感觉。
